# PROJECT_PLAN.md

## هدف محصول

اپلیکیشنی برای **کشف، دنبال‌کردن و یادآوری** نمایشگاه‌ها. شروع از تهران، با معماری‌ای که از روز اول آمادهٔ شهرهای دیگر ایران، سپس نمایشگاه‌های بین‌المللی و کاربران غیرایرانی است.

مزیت اصلی یک تقویم ساده نیست، بلکه **Discovery + Reminder + Feed شخصی‌سازی‌شده** است.

پنج سناریوی محوری کاربر:

1. «امروز چه نمایشگاه‌هایی برگزار می‌شود؟»
2. «در ۲۰ شهریور چه نمایشگاه‌هایی هست؟»
3. «نمایشگاه مبلمان کِی است؟»
4. «نمایشگاه‌های فناوری در ۳ ماه آینده»
5. «۷ روز قبل از این نمایشگاه به من یادآوری کن»

## فازبندی

هر فاز باید **قابل اجرا و قابل تست** تمام شود، نه نیمه‌کاره.

### فاز ۰ — پایه ✅ در حال انجام

- ساختار مخزن، `.gitignore`, `.editorconfig`
- مستندات: `PROJECT_PLAN` · `ARCHITECTURE` · `DATA_SOURCES`
- اسکلت NestJS + پیکربندی + `.env.example`
- `docker-compose` برای Postgres محلی
- workflow مربوط به GitHub Actions

**خروجی:** پروژه بالا می‌آید و `/health` جواب می‌دهد.

### فاز ۱ — مدل داده

- Migrationها برای همهٔ جداول (بند ۳۲ + جداول بین‌المللی‌سازی)
- افزونه‌های `pg_trgm` و `unaccent`
- تابع SQL نرمال‌سازی فارسی + `search_vector` + ایندکس GIN
- Seed توسعه: کشورها، تهران، venueهای اصلی، درخت دسته‌بندی
- **Seed شامل هیچ نمایشگاه واقعی نیست** (بند ۴۴)

**خروجی:** `npm run migration:run` روی Supabase موفق، اسکیما مستند.

### فاز ۲ — Ingestion

- `common/persian` — نرمال‌سازی + تست واحد
- `common/http` — Fetcher با rate limit، backoff، کش شرطی
- `EventroSource` با پارس بر پایهٔ برچسب متنی
- Normalizer + Dedup + Validation
- تست همهٔ Adapterها در برابر **fixture ذخیره‌شده**، نه شبکهٔ زنده

**خروجی:** `npm run sync -- --source=eventro --dry-run` نمایشگاه‌های واقعی تهران را استخراج می‌کند.

### فاز ۳ — API

- `GET /exhibitions` با فیلتر کامل و pagination اجباری
- `today` · `upcoming` · `date/:date` · `search` · `:id`
- `categories` · `venues` · `cities`
- Auth مهمان و حساب ناشناس دستگاه
- مستندات OpenAPI

**خروجی:** API روی Render مستقر و پاسخ‌گو.

### فاز ۴ — Sync Engine

- `SyncService` با اجرای منبع‌به‌منبع
- Change Detection + جدول `exhibition_changes`
- Source Monitoring (آخرین موفقیت، خطا، شمارش‌ها)
- Endpoint داخلی `/internal/sync` با هدر secret
- GitHub Actions cron هر ۱۲ ساعت + keepalive

**خروجی:** داده‌ها خودکار به‌روز می‌شوند و تغییرات ثبت می‌شوند.

### فاز ۵ — پنل ادمین

- CRUD نمایشگاه‌ها + تأیید + ادغام
- صف بازبینی: تکراری محتمل، تعارض تاریخ، confidence پایین
- مدیریت منابع: فعال/غیرفعال، وضعیت sync، خطاها

**خروجی:** ادمین می‌تواند تعارض‌ها را حل کند.

### فاز ۶ — اندروید (خواندن)

- خانه: امروز · فردا · به‌زودی
- تقویم شمسی با نشانگر روزهای دارای رویداد
- جستجو + فیلتر
- جزئیات نمایشگاه
- کش آفلاین با Room

**خروجی:** کاربر نمایشگاه‌های واقعی تهران را می‌بیند و جستجو می‌کند.

### فاز ۷ — Reminder و اعلان

- Favorite (نمایشگاه و دسته)
- Reminder با گزینه‌های ۳۰/۱۴/۷/۳/۱ روز و روز شروع + دلخواه
- آلارم محلی + بازسازی پس از reboot
- بازمحاسبه پس از تغییر تاریخ
- Deep link + اشتراک‌گذاری + مسیریابی

**خروجی:** Definition of Done کامل می‌شود.

### فاز ۸ — تثبیت

- تکمیل تست‌ها، build flavorها، مستندسازی نهایی

### پس از MVP

شهرهای دیگر ایران → Relay ایران و منابع رسمی → بین‌المللی → AI Search → Monetization

## Definition of Done برای MVP

- [ ] کاربر اپ را باز می‌کند و نمایشگاه‌های **واقعی** تهران را می‌بیند
- [ ] می‌تواند تاریخ انتخاب کند
- [ ] «مبلمان» را جستجو می‌کند و نتیجه می‌گیرد
- [ ] با دسته‌بندی و venue فیلتر می‌کند
- [ ] Favorite می‌کند
- [ ] Reminder می‌سازد و اعلان می‌گیرد
- [ ] با تغییر تاریخ نمایشگاه، Reminder خودکار جابه‌جا می‌شود
- [ ] داده‌ها خودکار sync می‌شوند
- [ ] تکراری‌ها ادغام می‌شوند
- [ ] ادمین تعارض‌ها را می‌بیند و حل می‌کند

## قوانین ثابت پروژه

1. **هیچ تاریخ نمایشگاهی تولید نشود.** نبود داده یعنی `UNKNOWN`، اختلاف یعنی `CONFLICT`
2. هر تاریخ به یک Source قابل ردیابی باشد
3. هیچ Secret در اپ موبایل نباشد؛ `.env` هرگز commit نشود
4. Seed data فقط برای توسعه
5. هیچ متن UI داخل کد پراکنده نشود
6. هیچ تبدیل دستی تاریخ نوشته نشود
7. تست Adapter در برابر fixture، نه شبکهٔ زنده
8. قبل از هر تغییر: Inspect → Understand → Plan → Implement → Test → Review
